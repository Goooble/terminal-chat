## Currently learning

- Checked exception propagation in Console.handleCommand: IOException comes from ServiceHandler.close; InterruptedException comes from Thread.join if the waiting console thread is interrupted. A throws declaration forwards possible failures to the caller rather than catching or generating them. connect's normal network failures are already caught and returned as false. Explained; current propagation through main can terminate the application for close/join failures.
- Registration flag review in the current minimal client: registered is only assigned false and never read; it currently provides no behavior. Transport checks in text only establish local socket/output availability, not server acceptance or peer liveness. Because rejected registration now closes the connection, an eventual confirmed session can use connection lifecycle after an initial OK handshake; the current interval between connect and OK still needs distinction if gating is added. Recommended removing unused flag until the receiver/handshake is implemented, without modifying code in this explanation turn.
- User identified a resource-lifecycle weakness: close() clearing socket/output in finally discards references even if socket.close throws, preventing deliberate retry or inspection. Explanation: failure leaves cleanup uncertain; retaining references permits another cleanup attempt, but does not mean the connection is usable. Recommended clearing references only after successful close; not implemented in this diagnostic turn.
- Latest working-tree check: files are back at the earlier connect-only ServiceHandler and constructor-based Console; do not restore the previously completed client automatically. User requested the next smallest coding iteration. Added only Console's volatile registered=false field and ServiceHandler AutoCloseable/close(). No loop, registration callback, or receiver exists in the current files.
- Socket lifetime clarification: candidate is local, but assigning socket=candidate stores a reference on the handler. The heap socket remains reachable after connect returns; explicit close releases the OS connection. close uses finally to clear socket/output references after attempting cleanup. Console's false-on-connect-failure wiring and true-on-server-OK handling remain for the input/receiver slices.
- ServiceHandler candidate versus socket: `candidate` is a local reference for preparing or reusing a TCP socket; `socket` retains the usable connection on the handler. They may reference the same object. The two variables do not represent registered versus unregistered users. Registration state must be updated separately based on server OK/error responses. Explained in response to the user's hypothesis; understanding not yet demonstrated.
- Imports versus instances and constructor injection: import makes a type name available; `new` creates an object; a constructor argument shares an existing object. Console and ServerHandler should receive the same Renderer rather than create separate terminal readers. Same-package classes need no import for one another. Explained after the user questioned Console's constructor; not yet demonstrated.
- Using Renderer from Console: create one Renderer in try-with-resources; call `readLine(prompt)` repeatedly in a loop; process each submitted line after Enter; null means stop, empty string is a blank submission, and `/quit` is interpreted by Console rather than Renderer. - Terminal line editing: incoming messages must preserve the edit buffer and cursor position. Plain `BufferedReader` cannot expose the partially typed line; a line editor such as JLine owns that state and `LineReader.printAbove` supports asynchronous output with redisplay. Recommended JLine behind Renderer rather than implementing terminal screen scraping; dependency choice is pending.
- Client lifecycle: automatic five-second retries were discussed and explicitly deferred. Unexpected loss displays `server error`; manual `/hello` starts a new attempt. `/quit` is intentional and should display `quitting application`. Unsent messages are not queued or replayed.
- Client concurrency design review: user proposed two classes, `Display` for terminal read/print and `ConnectionHandler` for socket communication and coordinating two loops. One thread reads server messages and prints them; the other reads console input and sends it. Serialize short output operations, but never hold that output lock during blocking terminal input. A print lock prevents application output interleaving but does not preserve partially typed terminal input. Shutdown must account for console reads that do not reliably unblock through thread interruption.
- Registration versus deregistration locking: registry insertion and conditional removal are already atomic via `ConcurrentHashMap`. The handler's registration monitor coordinates publishing the handler with sending its first `OK`; it does not enforce username uniqueness across different handler objects. Cleanup requires only atomic owned removal, tolerates in-flight send failures, and can close a socket without waiting for a blocked sender's monitor. Explained in response to the user's lock-asymmetry question; understanding not yet demonstrated.
- Thread execution and shared state in the implemented server: `Thread.start()` runs each handler's `run()` independently; calling another handler's `send()` still executes on the caller's thread. Local variables/input reader are confined to one handler thread, while the registry and outgoing writers are shared. Explained with Alice and Charlie sending to Bob; not yet demonstrated by the user.
- Monitor locks: synchronized instance methods lock the receiver (`this`); one writer at a time per recipient, with independent locks for different handlers. Java monitors are reentrant, allowing `handleHello` to call `send` while holding the same lock. Handshake lock orders `OK` before forwarded messages. Explained; understanding not yet checked.
- Concurrent registry operations: atomic `putIfAbsent` prevents duplicate-name races, conditional removal protects other registrations, and thread-safe lookup does not guarantee the recipient stays connected until a later send. Existing I/O error handling covers that race. Slow recipients can block senders; an outgoing queue per connection is a later alternative.
- `ClientHandler.run()` lifecycle: socket byte streams are wrapped in UTF-8 character readers/writers and buffered text I/O; `readLine()` waits for a line or EOF, assigns the result in the loop condition, and branches on registration state. `catch` reports I/O failure; `finally` unregisters the owning handler and closes its socket. Introduced through the user's selected code; understanding has not yet been demonstrated.
- `try` versus try-with-resources: `try (ServerSocket listener = ...)` closes the successfully created listener when the block exits, including on exceptions. `throws IOException` propagates I/O failures rather than catching them. The `while (true)` accept loop is intentionally indefinite and blocks in `accept()` between connections. Current `ChatServer.java` compiles; the exact IDE diagnostic on `while` is not yet known.
- `Optional<ClientHandler>` in `ConnectionRegistry.find`: `Map.get` returns null for an absent name; `Optional.ofNullable` represents a present handler or an empty lookup result explicitly. Introduced while explaining the selected method; user understanding is not yet demonstrated.
- Low-level design: assigning responsibilities to classes and objects, deciding who owns state, defining function inputs and outputs, and describing interactions in pseudocode. Design practice is pending.
